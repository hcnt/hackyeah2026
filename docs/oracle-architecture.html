The Attend Now oracle

How the face-recognition oracle turns a phone camera stream into one payout per attendee, what is built, and what is still needed before it works end to end. The public contract is docs/oracle-api.md; this page describes what sits behind it.

Flow 1

Joining: from one photo to the guest list

  • Before: the client loads GET /events/{id} for the event and the consent text, and calls attendance/test about twice a second while the camera is open. The test is stateless and stores nothing.
  • Submit checks in this order: request shape → wallet signature (valid, within 5 min, never used) → event exists and is not over → consent accepted and version known → the photo passes the quality checks (including looking straight at the camera) → face not already registered to another wallet in this event (cosine ≥ 0.50).
  • Stored: the normalised face signature, encrypted with the event's key, under the wallet that signed (the stage screen labels people by short wallet address; no name is collected). The photo is dropped as soon as the signature is made.
Flow 2

At the venue: from frames to one payout

  • Camera socket: the phone sends a JPEG, the oracle answers, the phone sends the next. No queue builds up, so a slow server just means fewer frames per second.
  • Detect and track: SCRFD finds every face; boxes are linked to tracks across frames by overlap (IoU ≥ 0.3). A track is dropped after 1.5 s unseen, or three frame intervals if frames are slow.
  • Recognise: unidentified tracks are embedded every frame, identified ones about once a second, in one batch per frame. Each embedding is compared with the event's guest list.
  • Identify: a track becomes a person once 3 of its last 5 embeddings match the same wallet at cosine ≥ 0.40. Time seen starts then.
  • Pay: once time seen reaches the event's minimum, the ledger moves the wallet to "pending" in a single step, so two frames or two cameras can't both trigger it. The payout runs in the background through PayoutSink.pay(); success marks the wallet paid and tells the stage screens, failure allows a retry after 5 s.
  • Stage: the latest frame with boxes goes to stage screens at most 5 times a second. Unknown faces carry no name and no score.

Privacy and security

Rules the code enforces

Face data

  • Photos and frames are never written to disk or logs.
  • Face signatures are stored encrypted with a per-event key held only in memory.
  • Keys, guest lists and tokens are destroyed when the event ends (checked every 60 s and on every access) or when the attendee leaves.
  • Unknown faces are never named or scored to any client.

Identity and money

  • Every action for a wallet carries that wallet's signature over a server-built message; replays and expired signatures are refused.
  • Only the event's organizer can pair cameras.
  • At most one successful payout per wallet per event from this process; the on-chain Payout account is the final guard.
  • Dev-only endpoints answer only when ENV=dev.

Known weaknesses

  • No liveness check: anyone can submit a photo of someone else. Production answer: a certified liveness provider in front of submit.
  • The join signature is not tied to the photos, so a leaked signature could be used with another face within 5 minutes.
  • No rate limit on the photo test endpoint (one face detection per call).
  • All state is in memory in one process: a restart during an event means attendees join again.

Scope

Build

  • Wallet login (sign a message)
  • Organizer: create and fund an event, dashboard, withdraw leftovers
  • Attendee: event list, separate consent screen, selfie, status and payout
  • Phone camera page streaming to the oracle

Decisions made here (change them if you disagree)

  • Login: our own "sign a message" check, not Supabase. Your CLAUDE.md says Supabase. A wallet login is about 40 lines in FastAPI with no external account, and the wallet is the identity anyway.
  • Postgres in Docker Compose (your choice). The image needs about 400 MB of disk, so it waits for the disk cleanup in M0.
  • Face signatures never touch the database. They stay in memory, encrypted with the event's key. A server restart during an event means attendees join again. That is acceptable for the demo and matches the privacy story.
  • One flat platform fee per payout, set in the program's config. The "higher of flat or percentage" rule can come later.
Contract 1 · on-chain

Solana program presence

Accounts

AccountAddress seedsFields
Config["config"]admin, oracle, treasury, fee_lamports: u64, bump
Event["event", organizer, event_id u64 LE]organizer, event_id: u64, oracle, treasury (copied from config at creation), start_ts: i64, end_ts: i64, reward_lamports: u64, fee_lamports: u64 (copied), max_payouts: u32, payouts_made: u32, min_seen_secs: u16 (used by the oracle, stored for transparency), bump, vault_bump

Payout["payout", event, attendee]event, attendee, paid_at: i64, bump. Its existence means "already paid".

Instructions

InstructionSignerDoesRejects when
init_configadminCreates Config with oracle, treasury and fee.Config exists.
update_configadminChanges oracle, treasury or fee. Running events keep their copies.Signer is not admin.
create_eventorganizerCreates Event and moves max_payouts × (reward + fee) plus the vault's rent-exempt minimum into Vault.start_ts ≥ end_ts; end_ts in the past; reward or max is 0.
update_eventorganizerChanges times, reward, max or minimum time seen, and tops up or refunds the vault difference.The event has started.
pay_attendeeoracleCreates Payout (oracle pays its deposit), sends reward from Vault to the attendee and fee to the treasury, and increments payouts_made.Signer is not the event's oracle; now outside [start_ts, end_ts]; payouts_made = max_payouts; Payout already exists (account-in-use error).
withdraworganizerSends everything left in Vault, rent minimum included, to the organizer.Before end_ts, unless no payouts were made yet (allows cancelling).
close_payoutoracleCloses a Payout account and returns its deposit to the oracle.Before end_ts, so nobody can be paid twice.

Time comes from the on-chain clock. Errors are a named enum: NotOracle, OutsideWindow, MaxReached, EventStarted, EventNotEnded, InvalidTimes, InvalidAmount.

Contract 2 · HTTP

Backend API

All under /api. "Wallet" means a base58 Solana public key. Authenticated calls send Authorization: Bearer <token>. Every query is scoped to the caller's wallet on the server; no wallet ID from the client is trusted.

CallWhoRequest → response
POST /auth/nonceanyone{wallet} → {message}: a login text with a one-time code that expires in 5 min.
POST /auth/verifyanyone{wallet, signature} → {token}: a session token valid for 12 h, after checking the signature against the message.
GET /eventsanyoneEvents from the chain joined with metadata: name, venue, times, reward, spots left, and a status worked out from the times when read.
POST /eventsorganizer{event_pubkey, name, venue, description} after the create transaction confirms. The server checks the on-chain organizer is the caller.
GET /organizer/eventsorganizerThe caller's events with going, paid and vault balance.
POST /events/{pk}/joinattendeeMultipart: consent_version, first_name, frames (3 JPEGs). Checks consent, one face per frame, the same person across frames, and a head turn. Rejects the signature if it already matches another wallet in this event. → {status: "on_list"}
DELETE /events/{pk}/joinattendeeLeaves the event and deletes the signature right away.
GET /events/{pk}/meattendee{status: "not_joined" | "on_list" | "paid", tx?}
POST /events/{pk}/camera-tokenorganizer→ {token, url}: a one-time camera token for this event, shown as a QR code.

The stage screen shows the camera's video as relayed frames with boxes drawn on them. Faces in the "unknown" state carry no name or score.

Inside the oracle

From frame to payout

  • Track faces across frames by box overlap, so one person keeps one track while they move.
  • Match each track against the event's guest list. A track counts as a person once its similarity is at least 0.40 on most recent frames.
  • Pay after the minimum time seen from the event. The payout goes into a queue and is sent once per wallet. If the chain answers "payout already exists", it is recorded as paid, so retries are safe.
  • Never store unmatched faces, frames or images. Logs keep only event, wallet, transaction and status.
  • Per-event key: guest-list signatures are kept encrypted with a key that lives only in memory. A background task in the same process checks every 60 s and destroys keys and guest lists of ended events. No separate worker container.
  • Oracle wallet: a hot key loaded from the environment through the settings class, holding only fee money.
Order of work

Milestones

  1. M0

    Unblock

    Clear disk space, install the Solana CLI and Anchor, add the oracle hostname to the existing tunnel, start Postgres in Docker Compose, create devnet wallets (admin, oracle, treasury, organizer, two attendees) and fund them.

    Done when anchor --version works and the wallets have devnet SOL.
  2. M1

    Program on devnet

    agent A

    All seven instructions plus tests: happy path, double payout, outside window, over max, wrong signer, early withdraw, edit after start.

    Done when tests pass on our machine and the program is deployed to devnet.
  3. M2

    Money moves when a face is seen

    agent B

    Backend: auth, events, join, oracle tracking, payout sender against devnet. Driven from the existing spike page before any real UI exists. This is the earliest moment the core demo works.

    Done when walking in front of the laptop webcam produces a devnet transaction visible on Explorer.
  4. M3

    Attendee and organizer app

    agent C

    Screens 1–7 from the sketch: wallet login, events, consent and selfie, status, dashboard, create and fund, withdraw.

    Done when the full flow runs in the browser from a fresh wallet.
  5. M4

    Phone camera and stage screen

    agent C

    QR pairing, phone camera page over HTTPS, live stage screen with boxes and payout feed.

    Done when a phone scanning the QR code drives payouts shown on the laptop screen.
  6. M5

    Rehearse

    Run the full demo three times with fresh wallets; write the pitch; record a backup video in case the venue Wi-Fi fails.

  7. S1

    Stretch: coupon NFTs

    Reward type "coupon", code list upload, burn to reveal a code.

How the agents split the work

  • A (program) and B (backend) run in parallel on separate folders. B codes against the account and instruction tables above, so it doesn't need to wait for A.
  • C (frontend) starts after B passes its end-to-end check, as your CLAUDE.md says.
  • Each agent gets: its folder, the folders it must not touch, the tests it must run, and "stop and report" if blocked.
  • I review every result, run the tests myself, and check the payout limits and the auth code by hand before anything is committed.
